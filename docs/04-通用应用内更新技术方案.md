# CodeDoc 安装包托管与应用内更新技术方案

> 状态：OSS/CDN/DNS/HTTPS 基础设施、CodeDoc 本仓库发布工具和 macOS 客户端已实施；GitHub Provider 尚未调研和实现
>
> 架构确认日期：2026-08-31；基础设施验收日期：2026-09-01
>
> 适用范围：CodeDoc macOS / Windows 桌面应用

> CodeDoc 当前产品策略：仅 macOS 启用应用内更新；Windows 只提供 NSIS EXE 人工安装与换版，不展示更新入口，也不执行启动检查。本文其余 Windows 更新内容保留为通用架构参考，不代表 CodeDoc 当前启用该能力。

## 一、文档目的

本文定义 CodeDoc 的安装包托管、应用内更新、签名校验、发布、灰度、回滚和运维标准。构建、归档、同步工具和发布记录都由 CodeDoc 仓库维护；后续应用应先在自己的仓库闭环，出现经过验证的公共需求后再提炼共享工具。

本文是技术架构和接入规范，不代表某个候选版本已经完成签名、公证或正式发布。当前能力仍以 CodeDoc README、维护基线和实际构建结果为准。

OSS/CDN/DNS/HTTPS 基础设施的真实资源、SSL 自动续期、服务器迁移和故障恢复以 `IdeaBoxWebsite/APP_UPDATE_INFRASTRUCTURE.md` 为运维主记录。CodeDoc 的 Provider 配置、发布命令和记录以本仓库 `ops/app-release/` 为准。两处只通过链接关联，不重复维护操作步骤，也不保存 AccessKey、证书私钥或服务器秘密。

## 二、已确认的架构决策

### 2.1 总体决策

- 统一公开下载域名：`https://download.ideaboxapps.com`。
- 使用一个阿里云私有 OSS Bucket 保存安装包、更新元数据和校验清单。
- 使用阿里云 CDN 作为唯一公开下载入口，由 CDN 私有回源 OSS。
- 每个应用、更新通道、操作系统和 CPU 架构使用独立路径。
- 第一阶段使用静态更新源，不建设版本检查微服务、数据库或管理后台。
- 官网只展示产品和人工下载入口，不保存安装包，不作为更新源。
- 安装包先发布并验证，`latest*.yml` 等可变更新指针最后发布。
- 用户源码、项目路径、文档内容和应用业务数据不得进入更新请求或发布日志。

CodeDoc 通过 `ops/app-release/release.config.json` 声明 `activeProvider` 和 `publishProviders`。当前只启用 OSS Generic Provider；GitHub Release 仅保留禁用的配置入口，待专项调研、实现和真实升级验收后才能启用。Provider 是构建时配置，切换后必须重新生成安装包。

### 2.2 为什么不使用现有官网目录

IdeaBoxWebsite 的部署会整体替换官网静态目录。把安装包放进官网工程或官网服务器目录会造成以下问题：

- 修改普通网页时重复上传大体积安装包；
- 官网备份反复复制历史安装包；
- 官网部署失败可能连带破坏更新源；
- 二进制产物容易误提交进 Git；
- 网站发布和应用发布无法独立回滚。

因此，官网与更新平台只通过 HTTPS 链接关联，发布生命周期必须分离。

### 2.3 为什么第一阶段不建设微服务

Electron 的 `electron-updater`、Sparkle、MSIX/App Installer 等成熟更新组件都能消费静态元数据和静态安装包。静态 OSS + CDN 已能满足版本检查、下载、断点续传、缓存和多应用隔离。

只有出现按账号授权、按组织分流、动态最低版本、实时停发后台或私有下载鉴权等明确需求时，才评估增加控制面服务。即使增加服务，安装包仍应由 OSS + CDN 直接分发，不经过应用服务器转发。

## 三、总体架构

```text
应用仓库 Tag / 手动发布
          │
          ▼
原生 CI Runner 构建
  ├─ macOS：签名 → 公证 → DMG / ZIP → 校验
  └─ Windows：签名 → NSIS / MSIX → 校验
          │
          ▼
上传带版本号的不可变产物到私有 OSS
          │
          ▼
通过 CDN 地址验证文件、签名、哈希、Range 请求
          │
          ▼
最后上传 latest*.yml / appcast.xml / .appinstaller
          │
          ▼
刷新短缓存元数据，按需预热安装包
          │
          ├──────────────► 官网人工下载
          │
          └──────────────► App 启动检查 / 手动检查 / 下载 / 安装
```

基础设施职责如下：

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| OSS | 保存安装包、元数据、校验清单和有限历史版本 | 不直接暴露上传凭据给客户端 |
| CDN | HTTPS、缓存、Range 下载、流量防护和公开下载域名 | 不生成版本、不判断业务资格 |
| CI | 构建、签名、公证、校验、上传和发布指针 | 不保存明文证书或长期共享密码 |
| App Main Process | 检查、下载、校验、安装和状态管理 | 不读取或上传用户源码 |
| 官网 | 展示版本说明和人工下载入口 | 不托管正式安装包，不决定应用内更新 |

## 四、域名、备案与 HTTPS

### 4.1 DNS

CDN 创建完成后，在 `ideaboxapps.com` 的权威 DNS 中增加：

```text
记录类型：CNAME
主机记录：download
记录值：阿里云 CDN 分配的 CNAME
TTL：按阿里云推荐值，初次切换期间使用较短 TTL
```

不得同时为 `download` 配置互相冲突的 A 与 CNAME 记录。生产验收必须确认公共 DNS 返回的 CNAME 与 CDN 控制台一致。

### 4.2 ICP 备案

`download.ideaboxapps.com` 是已备案主域名 `ideaboxapps.com` 的子域名。按阿里云当前说明，已备案网站域名的子域名作为中国内地 OSS/CDN 加速域名时无需再次单独申请 ICP 备案，但主域名备案必须持续有效。监管或云服务规则可能变化，每次新增加速区域或迁移云服务商前应重新核对官方要求。

### 4.3 HTTPS 证书

- CDN 必须配置能够覆盖 `download.ideaboxapps.com` 的有效证书。
- `download.ideaboxapps.com` 已使用 Let's Encrypt 单域名证书，并于 2026-09-01 完成公网 TLS 验收。
- 证书通过服务器上的 `acme.sh`、阿里云 DNS API 和 `ali_cdn` deploy hook 自动续签并部署到 CDN。
- 该长期免费方案依靠短期证书自动轮换，不是一张永不过期的证书；cron、RAM 最小权限、来源 IP 和公网证书日期必须持续监控。
- 可使用该子域名单域名证书，或能正确覆盖二级子域名的 `*.ideaboxapps.com` 泛域名证书。
- 证书配置位置是 CDN 控制台；启用 CDN 后，仅在 OSS 或原 Nginx 上配置证书不能保护客户端到 CDN 的连接。
- 强制 HTTP 跳转 HTTPS；确认 HTTPS 生效后再评估 HSTS，避免错误证书造成长时间不可恢复的客户端访问失败。
- 建立证书到期告警和自动续期验证，不以“控制台显示已托管”代替实际 TLS 验收。

## 五、OSS 与 CDN 基线

### 5.1 OSS

- Bucket 名称在实际创建阶段确定；Bucket 名不是客户端协议的一部分。
- Bucket 选择中国内地地域时，必须确认域名备案和 CDN 回源要求。
- Bucket 默认私有，禁止匿名写入和目录列举。
- CI 使用独立 RAM 发布身份，只授予目标 Bucket 和发布前缀所需的最小写入、读取与列举权限，不授予删除、改 ACL 或管理 Bucket 的权限。
- 历史版本清理由 OSS 生命周期或独立维护身份执行，不复用日常发布身份。
- 正式客户端和官网不得持有 OSS AccessKey、临时上传凭据或 Bucket 管理权限。
- 开启版本控制或等效的误覆盖恢复能力，并为旧版本设置明确生命周期规则。

### 5.2 CDN

- CDN 使用私有 Bucket 回源，公开访问只经过 `download.ideaboxapps.com`。
- 支持 `GET`、`HEAD` 和 Range 请求，确保大文件断点续传。
- 安装包、ZIP、blockmap 和签名文件禁止内容改写、页面优化或会改变字节内容的压缩处理。
- 桌面客户端通常不发送可靠 Referer，不得配置只允许官网 Referer 的规则，否则会阻断应用内更新。
- 第一阶段不启用需要动态签名参数的 URL 鉴权；如未来开启，必须先验证所用更新框架对带签名 URL 和重定向的兼容性。
- 配置带宽、流量、请求量和异常状态码告警，避免盗链或错误循环检查产生失控费用。
- CDN 访问日志不得被解释为产品使用分析；不得把用户项目、文件路径或业务内容写入 URL。

### 5.3 缓存策略

| 文件类型 | 建议策略 | 原因 |
| --- | --- | --- |
| 带版本号安装包、ZIP、blockmap | 长缓存，文件名不可变 | 同版本产物不得被覆盖 |
| `latest.yml`、`latest-mac.yml` | 不缓存或极短缓存 | 是稳定通道的可变发布指针 |
| beta/alpha 通道元数据 | 不缓存或极短缓存 | 需要快速停发和修正 |
| 按版本保存的校验清单 | 长缓存，文件名不可变 | 用于审计和人工校验 |
| 官网版本目录 JSON | 短缓存 | 仅供官网展示，不替代更新框架元数据 |

发布新版本后应刷新更新元数据缓存；安装包可按发布计划预热。缓存刷新不保证立即覆盖所有边缘节点，因此客户端和发布验收必须容忍短暂传播时间。

## 六、多应用目录协议

### 6.1 公共路径格式

```text
https://download.ideaboxapps.com/<app-slug>/<channel>/<platform>/<arch>/
```

字段约束：

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| `app-slug` | 全小写 ASCII，发布后不可随品牌文案任意改名 | `codedoc` |
| `channel` | 固定枚举，至少包含 `stable`、`beta` | `stable` |
| `platform` | 固定枚举：`mac`、`win`，后续按需扩展 | `mac` |
| `arch` | 固定枚举：`arm64`、`x64`、`universal` | `arm64` |

每个路径只服务一个应用、一个通道、一个平台和一个架构，不得让不同架构争用同一个 `latest-mac.yml`。

### 6.2 Electron 目录示例

```text
/codedoc/
├── stable/
│   ├── mac/
│   │   ├── arm64/
│   │   │   ├── latest-mac.yml
│   │   │   ├── CodeDoc-1.0.1-mac-arm64.zip
│   │   │   └── CodeDoc-1.0.1-mac-arm64.dmg
│   │   └── x64/
│   │       ├── latest-mac.yml
│   │       ├── CodeDoc-1.0.1-mac-x64.zip
│   │       └── CodeDoc-1.0.1-mac-x64.dmg
│   └── win/
│       └── x64/
│           ├── latest-win.yml
│           ├── CodeDoc-1.0.1-win-x64.exe
│           └── CodeDoc-1.0.1-win-x64.exe.blockmap
└── beta/
    └── ...
```

规则：

- DMG 用于 macOS 首次人工安装；ZIP 用作 `electron-updater` 的 macOS 更新载荷。
- NSIS EXE 用于 Windows 首次安装。`1.0.0` 仍采用 `internal-download`，不发布更新元数据；后续版本计划使用 `latest-win.yml` 提供版本发现和人工下载提示，Windows 客户端不自动下载安装。
- 更新元数据引用同一目录下带版本号的不可变文件。
- 不创建跨应用共享的 `latest.yml`。
- 不使用覆盖式 `CodeDoc-latest.dmg` 作为应用内更新的唯一源；官网如需要“最新版”按钮，应在部署时解析已验证的版本目录或使用独立短缓存指针。

### 6.3 新应用注册信息

每个新应用在接入前必须明确并评审以下字段：

```yaml
appSlug: codedoc
displayName: CodeDoc
appId: com.ideaboxapps.codedoc
owner: <维护负责人>
channels:
  - stable
  - beta
platforms:
  mac:
    architectures: [arm64, x64]
    updater: electron-updater
    signingTeam: <Apple Team ID，不记录私钥或密码>
  win:
    architectures: [x64]
    updater: electron-updater
    publisherName: <证书 Subject，不记录私钥或密码>
supportUrl: https://www.ideaboxapps.com/support
privacyUrl: https://www.ideaboxapps.com/privacy
```

该注册信息可以在后续阶段形成机器可校验的仓库配置，但第一阶段不得把凭据、证书内容或密码写入文件。

## 七、不同技术栈的复用边界

统一平台复用的是域名、OSS/CDN、路径规范、CI 安全门禁、发布顺序、日志和运维规则。客户端更新协议必须使用目标平台的成熟机制。

| 应用类型 | 基础设施 | 推荐更新机制 |
| --- | --- | --- |
| Electron macOS / Windows | 完整复用 | `electron-updater` + Generic Provider |
| 原生 macOS 官网分发 | 完整复用 | Sparkle appcast 与签名机制 |
| Windows 原生或 .NET | 完整复用 | MSIX/App Installer 或经评审的成熟框架 |
| Mac App Store | 仅可复用官网资料和归档 | 由 App Store 更新，不自建安装更新 |
| iOS / iPadOS App Store | 仅可复用官网资料 | 由 App Store 更新，不在应用内下载安装包 |
| Android 官网分发 | 可复用 OSS/CDN | 另行设计 APK 签名、权限和安装确认流程 |

不得为了“统一协议”自行实现跨平台二进制替换器，也不得绕过系统商店的更新规则。

## 八、Electron 客户端标准

### 8.1 组件选择

Electron 应用使用与 electron-builder 配套的 `electron-updater`，选择 Generic Provider 并指向当前应用、通道、平台和架构的静态目录。

客户端不得自行下载后直接覆盖正在运行的 App，也不得由 Renderer 实现网络下载或启动安装器。

### 8.2 进程边界

```text
Renderer 更新界面
      │ 窄类型 IPC
      ▼
Preload contextBridge 白名单 API
      │
      ▼
Main Process UpdateService
      │
      ▼
electron-updater → download.ideaboxapps.com
```

建议的 Renderer API 仅包含：

- 获取当前更新状态；
- 用户主动检查更新；
- 用户确认后开始下载；
- 取消尚未完成的下载（框架支持时）；
- 下载完成后请求重启安装；
- 订阅经过清洗的进度和错误状态。

不得向 Renderer 暴露原始 `ipcRenderer`、文件系统路径、任意 URL 请求、OSS 地址或安装器执行能力。

### 8.3 状态机

```text
idle
  → checking
  → up-to-date
  → available
  → downloading
  → downloaded
  → installing
  → error
```

要求：

- 状态转换由 Main Process 单点维护；
- 重复检查和重复下载必须幂等；
- 错误信息转换成稳定错误码和用户可理解文案，不把本地敏感路径直接展示或上传；
- 开发环境默认不连接正式更新源；
- 只有打包后的候选版本才执行真实应用内更新验收。

### 8.4 产品行为

- 启动后延迟检查，并加入随机抖动，避免所有客户端同时访问元数据。
- 每次运行最多自动检查一次；设置页保留“检查更新”。
- 自动检查未发现更新时保持安静；手动检查必须明确返回“已是最新版本”或错误。
- 默认 `autoDownload = false`，由用户点击后下载。
- 展示目标版本、纯文本发布说明、安装包大小和下载进度。
- 下载完成后提供“立即重启安装”和“稍后安装”。
- 正在扫描、清洗、排版、导出或存在未保存状态时，不得静默退出安装。
- 更新失败后保留当前可运行版本，并提供官网人工下载入口。
- 不把远程 HTML 直接注入 Renderer；发布说明使用纯文本或受控 Markdown 子集。

### 8.5 网络与隐私边界

- 更新模块只访问经过白名单确认的 HTTPS 域名与路径。
- 请求只需要当前版本、应用标识、平台、架构和通道。
- 不上传用户源码、项目路径、导出内容、著作权人信息、最近项目或设备文件列表。
- 不因更新功能新增账号、广告、分析 SDK 或跨应用用户画像。
- 产品仍可声明源码处理本地完成，但隐私文档必须如实说明应用会访问更新服务。

## 九、签名、公证与供应链安全

### 9.1 macOS

正式官网分发及应用内更新至少要求：

- 使用有效的 Developer ID Application 证书签名 App；
- 启用 Hardened Runtime；
- 所有嵌套可执行文件完成正确签名；
- 提交 Apple 公证并成功；
- 对可 staple 的分发产物执行 staple；
- 通过 `codesign`、`spctl` 和 `stapler` 验收；
- 在干净机器上从 DMG 首次安装，再从旧版完成应用内更新。

macOS 更新必须保持可接受的签名身份。证书轮换前要进行跨证书升级测试，不得在证书失效后才首次验证更新兼容性。

### 9.2 Windows

- 正式 NSIS 或 MSIX 产物必须使用受信任的 Authenticode 方案签名。
- `publisherName` 必须与证书 Subject 匹配。
- 开启更新包代码签名验证，不得为了绕过证书错误而关闭验证。
- 证书轮换期间按框架能力允许旧、新发布者身份，并在轮换完成后移除旧身份。
- 测试默认目录和用户自选安装目录的升级行为。
- 不使用可能绕过完整载荷签名校验的 Web Installer 作为默认更新目标。

### 9.3 哈希与 TLS 的关系

HTTPS、更新元数据中的 SHA-512、人工发布清单中的 SHA-256 和操作系统代码签名承担不同职责，不能互相替代：

- HTTPS 保护传输通道；
- SHA-512/更新元数据验证下载文件与发布描述一致；
- SHA-256 清单用于发布审计和人工复核；
- Developer ID / Authenticode 证明发布者身份并保护可执行代码完整性。

### 9.4 凭据管理

- 私钥、证书密码、Apple 凭据、OSS AccessKey 和 CDN 管理凭据不得提交到仓库。
- CI 使用专用秘密存储；日志禁止打印秘密值和完整签名材料。
- 发布身份按最小权限拆分；普通 PR 构建不得拥有生产上传和签名权限。
- Tag 发布需要受保护分支、受保护 Tag 或人工审批门禁。
- 正式构建设置“缺少签名即失败”，不得静默降级为未签名安装包。

## 十、版本、通道与发布规则

### 10.1 版本规则

- 使用 SemVer 风格版本号，并保证 App 内版本、安装包名、元数据和 Git Tag 一致。
- 已发布版本号不可复用，即使产物上传错误也必须使用更高版本修复。
- `stable` 只接收完成全部签名、公证和升级验收的正式版本。
- `beta` 用于真实更新链路验证，不得让正式用户默认加入。
- 构建号与展示版本的映射由各产品定义，但必须能唯一追溯到源码提交和 CI 运行。

### 10.2 原子发布顺序

每个平台和架构必须按以下顺序执行：

1. 校验工作区、版本号、依赖锁和许可证。
2. 在目标平台原生 Runner 构建。
3. 完成签名、公证和本地产物验收。
4. 生成更新元数据、blockmap 和校验清单。
5. 上传带版本号的不可变产物，不上传 `latest*` 指针。
6. 通过 CDN 地址执行 `HEAD`、完整下载或抽样下载、文件大小、哈希、签名和 Range 验证。
7. 从已安装的上一正式版本在 beta 通道完成真实更新。
8. 上传 stable 的 `latest*.yml` 等可变指针。
9. 刷新元数据缓存，按需预热大文件。
10. 再次从公网执行版本检查和下载冒烟。
11. 更新官网人工下载链接和发布说明；官网失败不得反向撤销已发布更新指针。

禁止先发布 `latest*.yml` 再上传安装包。该错误会让客户端看到一个暂时或永久不存在的版本。

### 10.3 CI 复用

多应用应复用一个受版本控制的发布工作流模板，输入至少包括：

- `appSlug`；
- 产品显示名；
- 版本号；
- 通道；
- 平台和架构矩阵；
- 产物 glob；
- OSS 目标前缀；
- 签名配置引用；
- 公网验收基础 URL。

模板只负责通用门禁；每个应用仍保留自己的构建命令、签名身份、测试和发布审批。共享工作流升级必须固定版本，先在 beta 通道验证后再推广。

## 十一、灰度、停发与回滚

### 11.1 灰度

Electron 可在 `latest.yml` / `latest-mac.yml` 中使用框架支持的 `stagingPercentage`。使用前必须确认当前锁定版本的 `electron-updater` 行为，并验证同一客户端在灰度期间分组稳定。

对于早期用户量较小的产品，优先采用 beta 通道和内部设备验证；没有错误监控和用户反馈通道时，不应把百分比灰度误认为可观测的安全发布。

### 11.2 停发

发现问题时：

1. 立即停止扩大灰度并暂停 stable 元数据发布。
2. 保留问题版本产物和 CI 证据用于审计，不覆盖同名文件。
3. 对尚未升级的客户端，可将 stable 指针恢复到上一安全版本。
4. 对已经升级的客户端，发布更高版本修复；不得依赖版本号降级。

### 11.3 回滚限制

应用内更新不是数据库事务，也不能保证跨版本自动恢复用户状态。每个应用必须单独评估配置文件、缓存、项目格式和数据迁移的向后兼容性。

若新版本写入了旧版本无法读取的数据，简单恢复旧安装包并不等于安全回滚。因此：

- 配置迁移优先保持向后兼容；
- 不可逆迁移必须独立评审；
- 更新前不得静默删除用户数据；
- 更新失败必须尽量保留当前安装和用户文档；
- 数据恢复步骤必须进入该应用的发布说明和运维手册。

## 十二、监控、日志与费用控制

### 12.1 基础监控

- DNS 与证书有效期；
- CDN 4xx/5xx、回源失败和命中率；
- 下载流量、峰值带宽和异常请求量；
- OSS 存储量、版本数量和生命周期执行结果；
- 每个平台元数据及其目标文件是否同时存在；
- 最新 stable 版本的签名、公证和哈希验收结果。

### 12.2 隐私边界

默认只使用 OSS/CDN 提供的基础访问日志和聚合指标。客户端不新增设备指纹、用户账号、项目标识或遥测 SDK。若未来需要更新成功率统计，必须作为独立隐私评审任务，先定义数据最小化、告知、保留期和退出机制。

### 12.3 费用保护

- 设置日流量、月流量和峰值带宽告警；阈值在开通服务时根据套餐填写，不在本文猜测。
- 对安装包使用长缓存，减少 OSS 回源流量。
- 保留必要历史版本，过期产物按经批准的生命周期策略归档或删除。
- 不允许客户端高频轮询；自动检查使用延迟、抖动和运行期去重。
- 发现异常盗链时先限流和分析日志，不直接启用会阻断桌面客户端的 Referer 白名单。

## 十三、官网集成

官网可以为每个产品展示：

- 当前正式版本；
- 发布日期；
- macOS Apple Silicon、macOS Intel、Windows 等人工下载按钮；
- SHA-256 清单链接；
- 系统要求、签名状态和安装说明；
- 更新说明与历史版本页面。

官网不得：

- 把安装包复制到 Git 仓库；
- 在浏览器中持有 OSS 上传凭据；
- 通过修改网页内容直接生成或覆盖 `latest*.yml`；
- 宣称未完成签名、公证或干净机器验证的包是正式发布版；
- 用官网部署替代应用发布审批。

官网的版本展示可以读取独立的、非安全关键的短缓存 JSON，但客户端是否更新仍以对应平台的正式更新元数据和签名校验为准。

## 十六、变更管理

以下修改必须经过专项评审：

- 下载域名、Bucket、CDN 服务商或路径协议变更；
- App ID、`appSlug`、签名主体或 Windows Publisher 变更；
- 从静态更新源切换到动态微服务；
- 引入强制更新、账号分流或设备标识；
- 开启 URL 鉴权、Referer 防盗链或跨域重定向；
- 删除历史安装包或缩短保留期；
- 更换更新框架或关闭签名校验；
- 修改 stable/beta 的版本选择规则。

文档维护者应在云服务、更新框架、签名政策或商店规则发生变化时复核本文。任何偏离本文的产品实现都必须记录原因、影响、回滚方式和批准人，不能以临时脚本长期绕过标准流程。
