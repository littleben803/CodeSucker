# CodeDoc 安装包托管与应用内更新方案

> 更新日期：2026-09-03
> 状态：GitHub Release 与 OSS 发布链路均已实现；两种 Provider 的真实发布、公网下载和 macOS 应用内升级均已验证。

## 一、目标

CodeDoc 在自己的仓库内完成版本设置、安装包构建、发布、校验和回执归档，不依赖其他应用或项目。

系统同时支持两种托管方案：

- GitHub Release：默认方案，承担公开安装包托管和 macOS 应用内更新。
- 阿里云 OSS：备选方案，可以独立发布和切换。

维护人员只需修改项目配置并执行既有脚本，不需要修改客户端业务代码。

## 二、配置入口

唯一配置入口是 `ops/app-release/release.config.json`：

```json
{
  "activeProvider": "github",
  "publishProviders": ["github"]
}
```

- `activeProvider` 决定安装包内置的应用更新源，可选 `github` 或 `oss`。
- `publishProviders` 决定不指定 `--provider` 时使用的发布目标。
- `providers.github.appUpdateEnabled` 控制 GitHub 能否作为客户端更新源。
- `providers.github.writeEnabled` 控制 GitHub 发布脚本能否真实写入。

`activeProvider` 是构建时配置。修改后必须重新生成安装包，已安装的旧版本不会自动改变更新源。

临时发布到非默认 Provider 时使用显式参数：

```bash
npm run release:sync -- --provider github --channel stable --targets all
npm run release:sync -- --provider oss --channel stable --targets all
```

## 三、Provider 方案

### 3.1 GitHub Release

发布仓库：`littleben803/CodeSucker`

每个正式版本对应一个 Git Tag 和一个 GitHub Release，例如：

```text
版本：1.0.2
Tag：v1.0.2
Release：CodeDoc 1.0.2
```

Stable Release 包含：

```text
CodeDoc-<version>-mac-arm64.dmg
CodeDoc-<version>-mac-arm64.dmg.blockmap
CodeDoc-<version>-mac-arm64.zip
CodeDoc-<version>-mac-arm64.zip.blockmap
CodeDoc-<version>-mac-x64.dmg
CodeDoc-<version>-mac-x64.dmg.blockmap
CodeDoc-<version>-mac-x64.zip
CodeDoc-<version>-mac-x64.zip.blockmap
CodeDoc-<version>-win-x64.exe
CodeDoc-<version>-win-x64.exe.blockmap
latest-mac.yml
latest-win.yml
```

Beta Release 额外包含 `beta-mac.yml`，并标记为 Prerelease。

GitHub 发布顺序：

1. 校验远端 Tag 与本地构建源码提交一致。
2. 创建 Draft Release。
3. 上传带版本号的安装包、更新载荷和 blockmap。
4. 上传聚合更新元数据。
5. 按文件名、大小和 SHA-256 复核全部资产。
6. 全部通过后公开 Release。
7. 生成聚合发布回执并打印最终下载地址。

脚本不会覆盖同名资产。执行中断后再次运行，会校验已有资产并跳过一致文件；发现同名但内容不一致时立即停止。

### 3.2 阿里云 OSS

OSS 保留为独立备选 Provider，使用 Generic Update Provider 协议。

发布流程负责校验本地归档、上传不可变产物、最后发布更新元数据、复核公网文件并取回发布回执。OSS 凭据只存在于受控发布环境，不进入客户端、项目配置、日志或 Git 仓库。

## 四、客户端更新逻辑

### 4.1 macOS

macOS 使用固定版本的 `electron-updater 6.8.9`，支持 Apple Silicon 和 Intel。

当 `activeProvider` 为 `github` 时，客户端使用原生 GitHub Provider：

```text
provider: github
owner: littleben803
repo: CodeSucker
tagNamePrefix: v
stable channel: latest
beta channel: beta
```

当 `activeProvider` 为 `oss` 时，客户端使用 Generic Provider，并按通道、平台和架构定位更新目录。

两种 Provider 使用同一套交互与安全策略：

- 窗口 `ready-to-show` 后延迟约 2～3 秒检查。
- 只检查，不自动下载安装包。
- 发现新版本后显示更新红点和“立即更新”按钮。
- 用户确认后才下载。
- macOS 下载完整更新 ZIP，不使用差分下载或历史更新缓存重建新版本。
- 下载完成后由用户确认重启安装。
- 扫描、处理或导出任务进行中时禁止安装。
- 开发版不连接正式更新源。
- 更新器将脱敏诊断写入应用日志目录的 `updater.log`，用于区分网络、完整性、签名、存储和本地更新服务错误。

macOS 更新载荷使用完整 ZIP，DMG 用于首次安装和人工下载。`.blockmap` 继续作为发布资产保留，但当前客户端不使用差分更新。正式包必须完成 Developer ID 签名、公证、staple 和 Gatekeeper 验证。

### 4.2 Windows

Windows 发布 NSIS EXE、blockmap 和 `latest-win.yml`。

当前只提供版本发现和人工下载所需的发布能力，不启用自动下载与静默安装。完成 Windows 正式代码签名和专项验收前，不扩大这一边界。

## 五、项目内发布控制面

发布工具位于 `ops/app-release/`：

- `release.config.json`：Provider、应用、通道和目标配置。
- `sync-release.mjs`：整批发布入口，默认 dry-run。
- `github-release.mjs`：GitHub Draft、上传、校验、公开和断点恢复。
- `publish-via-host.mjs`：OSS 服务器交接。
- `prepare-release.mjs`：构建清单校验和 prepared 回执。
- `release-records.mjs`：聚合 prepared/published 记录。
- `server/`：OSS 发布服务器工具。

本地构建归档位于 Git 忽略目录：

```text
ops/app-release/.release-work/
```

版本记录位于：

```text
ops/app-release/releases/<app>/<channel>/<version>/prepared.json
ops/app-release/releases/<app>/<channel>/<version>/published.json
```

每个阶段只保留一个聚合 JSON，平台和架构记录放在 `targets` 数组中。

## 六、标准发布流程

### 6.0：检查所有版本字段一致
```bash
npm run version:check
```

### 6.1 统一升级版本号并更新 docs/CHANGELOG.md

```bash
npm run version:set -- <version>
npm run verify
```

`version:set` 会同步 workspace 版本，并在 `docs/CHANGELOG.md` 顶部生成版本模板。

### 6.2 打 tag 并 push 到远端

版本提交推送后创建附注 Tag：

```bash
git tag -a v<version> -m "CodeDoc <version>"
git push origin v<version>
```

Tag 必须指向用于构建的源码提交，发布后不得移动或复用。

### 6.3 构建并归档三个平台安装包

```bash
npm run package:release -- \
  --channel stable \
  --targets all \
  --yes
```

正式构建要求工作区干净，三个目标必须来自同一个提交。

### 6.4 发布前预演

```bash
npm run release:sync -- \
  --provider github \
  --channel stable \
  --targets all
```

预演只展示计划，不写服务器或云端。

### 6.5 正式发布 GitHub Release

使用预演输出的确认字符串：

```bash
npm run release:sync -- \
  --provider github \
  --channel stable \
  --targets all \
  --execute \
  --confirm '<dry-run 输出的确认字符串>'
```

成功后终端打印三个安装包的最终下载地址和 `published.json` 路径。

## 七、安全与失败恢复

- 默认 dry-run；只有 `--execute` 和完全匹配的确认字符串同时存在时才允许写入。
- 不在配置、参数、清单、回执或日志中保存 Token、AccessKey、证书和私钥。
- GitHub 公共仓库客户端更新不需要 Token。
- 上传前验证 Tag、源码提交、构建清单、文件大小和哈希。
- 更新元数据最后发布，避免客户端读取到未完成版本。
- GitHub 使用 Draft 隔离未完成发布，支持安全恢复，不覆盖同名资产。
- OSS 使用隔离目录、阶段标记和互斥锁恢复中断任务。
- 发布失败不会删除已有稳定版本，也不会自动修改 Git Tag。

## 九、维护约定

- 新应用优先在自己的仓库内闭环，不复制 CodeDoc 的发布记录或安装包。
- 有稳定复用需求时再提取通用工具，不建立跨应用发布控制面。
- 修改 Provider 配置后必须重新打包验证。
- 修改发布脚本后至少运行发布工具测试和 `npm run verify`。
- 发布完成后提交 prepared/published 回执，不提交安装包、临时目录或本地环境文件。
